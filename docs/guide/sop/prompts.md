# 团队协作 SOP · 需求输入提示词

`biz-product-docs/prompts/` 是 `/agile:prd` 的需求描述源：**提示词是「源」，PRD 是编译产物**——需求变更（范围 / 规则调整）优先改提示词稿、重跑 `/agile:prd` 再生成；细节修订（补一条 AC、勾选状态、文字勘误）直接改 PRD/AC 即可，重跑时人工修订会被检测采纳、不会覆盖。工作区初始化时已预建 `prompts/README.md`（[初始化](/guide/sop/init)）。

提示词工作流是**可选流程**：不用提示词稿时，`/agile:prd` 一切照旧（直接贴需求描述）。

## 目录与文件约定

| 约定 | 说明 |
|---|---|
| 一需求一稿 | 文件名 = 需求编号（`STO-001.md`、`BUG-003.md`），平铺 `prompts/` 目录，不建子目录 |
| 首行 H1 | `# <编号> <主题>`（如 `# STO-001 订单导出三个月流水`）——编号排序天然时序，首行主题可 grep |
| 配套材料 | 截图、纪要、外部文档要点放 `requirements/<编号>/`，稿内以相对链接引用；`prompts/` 只放提示词本体 |
| 交付后保留原地 | 即需求理解的历史记录，不归档、不移位 |
| 导航登记 | 不逐条登记库根导航、不设归档分组、无 frontmatter——编号即索引，git 即历史 |

## 推荐骨架

自由 markdown，仅推荐不强制（骨架同时写在 `prompts/README.md`）：

```markdown
# STO-001 订单导出三个月流水

## 一句话
（做什么、给谁用、解决什么问题）

## 细节与约束
- 业务规则 / 边界 / 异常路径
- 非功能点（性能、权限、数据量…）

## 明确不做
- 排除项

## 参考
- 外部文档链接、旧版行为、会话纪要要点
```

## 工作流程：四个阶段

与 AI 沟通写提示词就是自然对话——不设命令、不设问答模板；唯一纪律是**聊出来的结论要落盘到 `prompts/<编号>.md`**，不留在会话里（会话跨轮即丢，文件进 git 可 diff、可重跑）。

| 阶段 | 谁做 | 怎么做 |
|---|---|---|
| ① 起草 | 你 + AI | 直接说需求想法，AI 按骨架维度有缺才问（用户/场景、核心规则、边界、明确不做），有共识后落稿 |
| ② 打磨 | 你 + AI | 读稿后零散说调整，AI 改稿；或自己在 VS Code / GitHub Web 改。可跨会话——源在 git 里，新会话重读继续 |
| ③ 编译 | 你触发 | 稿子稳定后 `/agile:prd STO-001` 生成 PRD/AC；是否定稿由你判断，AI 不替你决定 |
| ④ 变更 | 你 + AI | 需求变更改稿 → 重跑 `/agile:prd STO-001`；已进入开发的需求走[协作与文档规则](/guide/sop/collab)的变更流程知会下游 |

## /agile:prd 的三种工作方式

| 方式 | 触发 | 行为 |
|---|---|---|
| 读稿编译 | `prompts/<编号>.md` 存在 | 以提示词稿为需求描述，命令行里的额外文字作为叠加补充；PRD 头部登记来源稿路径 |
| 澄清落稿 | 稿不存在、只给了编号或描述明显不足 | AI 先对话澄清并落稿给你确认；确认后继续生成 PRD，说「先只落稿」则停在草稿 |
| 直接编译 | 命令带了完整需求描述 | 按描述直接生成（传统用法，无提示词稿） |

自由命名的提示词稿（非编号命名）用 `--prompt <路径>` 显式指定。命令细节见[命令详解 · /agile:prd](/plugin/commands)。

## 边界

- **轻量通道**（BUG / OPS 一句话需求，见[轻量通道](/guide/sop/lite)）无需提示词稿；确需时按同约定放置即可。
- 流程本身不进知识库；团队在使用中沉淀出领域性经验（如「我们的需求提示词必须写数据口径」）才适合经 `/agile:knowledge capture` 入库。
